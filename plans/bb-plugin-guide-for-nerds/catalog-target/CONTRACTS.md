# Suggested later worker contracts (research only)

Each catalog exports plain readonly records and one release receipt ID. No host control imports are necessary to document exports. Local catalog data remains owned by the new plugin. The retained SDK declarations are evidence only: use the exact public npm development dependency for compilation, never a TypeScript path alias into this research directory.

Theme records: `{ id: bridgeName, variable, utility, category, demonstrationKind, description, sourceRef, compatibility }`. Preserve the exact bridge expression for calculated radius entries and the `variables[]` dependencies. For color demos the copied name is the semantic variable, not `--color-*` or a computed value. `utility` is a real class such as `bg-background`; `bridgeName` is `--color-background`. Utility examples in the research inventory are illustrative valid utility families, not a guarantee every class is emitted by every plugin build. Line-height subproperties are modifiers of typography, not independent colors. Keep the 56 color records separate from the 21 font/radius/shadow/typography declarations if the section focuses on colors; account for every declaration with a documented non-color classification. Standard Tailwind defaults and tw-animate-css are dependencies rather than BB semantic palette tokens.

Native records are discriminated unions:

* `{ kind: "host", exportName, importFrom: "@get-bb/plugin-sdk/app", experimental, description, sourceRef, compatibility }` for every renderable host export.
* `{ kind: "registry", registryName, target: "@bb/<name>", classification: "renderable-source" | "nonvisual-helper", helperKind?, description, files, dependencies, registryDependencies, sourceRef, compatibility }` for every registry entry.

Compatibility should carry `{ targetBb: "0.45.0", targetSdk: "0.6.15", deployedSourceBb: "0.44.0", deployedSourceSdk: "0.5.29", status: "present-in-both-source-contracts" | "newer-host-only" | "removed-from-target" | "unknown-runtime", note? }`. Registry source ownership does not imply independence from host APIs: `icon` forwards to the SDK; `question-form-host` is a host hook. Do not label all registry entries experimental merely because some transitive SDK calls are experimental. The registry declares no experimental metadata; classify that as unspecified and preserve explicit SDK flags separately. Do not confuse a nonvisual provider/hook with a visible UI experience.

All theme/native records refer to one immutable release receipt. Worker output exports can be `THEME_CATALOG`, `HOST_EXPERIENCE_CATALOG`, `REGISTRY_CATALOG`, and `CATALOG_RELEASE`. These are proposed plugin-local data exports, not authorization to implement or publish a shared package.

Completeness acceptance compares exact identity sets with retained source, rejects duplicates, and checks semantics as well as counts. Verify bridge variable/expression/utility correspondence; exact runtime export spelling and import path; renderable versus helper classification; registry dependency closure/file targets; descriptions/experimental flags; release receipt and compatibility markers. Detect additions/removals and content hashes changed since the previous target. Preserve explicit helper records instead of dropping them from the native catalog.

Required negative mutations: delete a color token while leaving count metadata untouched; replace a valid host export with `experimental_UrlLink` or a nonexistent export; replace/remove a registry target while preserving its label. Each must make the comparison fail. Also reject duplicate IDs, a helper relabeled as renderable, an altered registry file/import, and mismatched BB/SDK receipt. A removed-target fixture must use a synthetic invalid name or a deliberately mutated source fixture: this release has no removed registry names relative to deployed upstream. These gates are later implementation acceptance requirements; no catalog implementation or negative fixture was added here.
